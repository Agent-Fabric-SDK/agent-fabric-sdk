# Spec format

A single declarative YAML file, versioned in your own repo, validated by
pydantic models. [`Governance.export()`](/concepts/environments) emits
fragments of exactly this format — the two features share one schema, and
that is deliberate; they must not diverge.

```yaml
apiVersion: fabric/v1
kind: FabricSpec
metadata:
  name: hr-agent-tools
  environment: Sandbox
  businessGroup: 5a1b...

mcpBridges:
  - name: hr-tools
    gateway: managed-omni-eu-1
    apis:
      - assetId: employee-api
        version: 1.2.0
        upstream: https://internal.acme.com/employees
        tools:
          - name: get_employee
            method: GET
            resource: /employees/{id}
            description: Fetch an employee record by ID.
            inputSchema: auto        # derive from the OAS/RAML spec
          - name: search_employees
            method: GET
            resource: /employees
            description: Search employees by department or title.
            inputSchema:
              type: object
              properties:
                department: {type: string}
              required: [department]
    policies:
      - assetId: rate-limiting-sla-based
        version: 1.2.0
        config:
          rateLimits:
            - maximumRequests: 100
              timePeriodInMilliseconds: 60000
```

## Design notes

### `inputSchema: auto` is the highest-leverage feature

Set `inputSchema: auto` and the tool's JSON Schema is derived from the API's
published OAS/RAML spec in Exchange — you don't hand-write one field at a
time. This is what makes bulk conversion of, say, 200 APIs into MCP tools
tractable.

It's implemented as a **local OAS/RAML → JSON Schema transform**, not a call
to any control-plane endpoint. That means it:

- runs offline in CI, with no network dependency on Anypoint,
- produces a plain, reviewable diff in a pull request, the same way any other
  generated-code diff would,
- survives the [Terraform-generation fallback](/provisioning#the-fallback-generate-terraform-instead)
  intact, since it never depended on a provisioning API in the first place.

Fall back to an explicit `inputSchema` object (as `search_employees` does
above) whenever the auto-derived shape isn't what you want exposed to a model.

### DataWeave is a hard boundary

<Callout type="warning">
  MCP Bridge's HTTP mapping uses DataWeave expressions for non-trivial
  parameter extraction. The spec accepts a raw `httpMapping.dataweave` string
  as a passthrough field — the SDK makes no attempt to generate or parse
  DataWeave. This is a documented limitation, not a gap that gets filled in
  later.
</Callout>

If a tool needs request/response shaping beyond a straight field mapping,
write the DataWeave script yourself and paste it into `httpMapping.dataweave`.
The SDK treats it as an opaque string end to end.

### No secrets in the spec

Never put a credential value in `fabric.yaml`. Reference it instead, and let
`apply` resolve it against the secrets backend at apply time:

```yaml
upstreamAuth: ${secret:anypoint-secrets-manager/hr-api-key}
```

The spec file is meant to be safe to commit and safe to review in a PR diff —
a secret reference costs nothing to leak; a secret value does.
