# Plan & apply

`agent-fabric plan` diffs your `fabric.yaml` against live state and shows
exactly what would change, without changing anything:

```bash
$ agent-fabric plan -f fabric.yaml
  + mcpBridge  hr-tools                    (create)
  ~ mcpBridge  finance-tools               (update: +1 tool, ~1 description)
      + tool   list_invoices
      ~ tool   get_invoice   description changed
  - policy     rate-limiting-sla-based     on hr-tools (remove)

3 changes. Run `apply` to proceed.

$ agent-fabric apply -f fabric.yaml --auto-approve
```

## Requirements

- **Read-before-write, always.** Fetch current state, diff, render, then
  apply. `apply` never blind-PUTs a resource.
- **Idempotent.** Re-running `apply` with no spec change produces zero API
  calls that mutate anything.
- **`--dry-run` and `--out plan.json`** exist for CI gating: a GitHub Action
  posts the rendered plan as a PR comment, and `apply` runs only on merge.
- **Partial-failure handling.** Resources are applied in dependency order.
  On the first failure, `apply` stops and reports exactly what was applied and
  what was not — it does **not** attempt automatic rollback. Silent partial
  rollback in a control plane is worse than a clear stop; the operator
  re-plans from the reported state instead.
- **Drift detection.** `agent-fabric drift` compares live state against the
  spec and exits non-zero if they've diverged. Run it on a schedule — it
  catches console changes that bypassed the pipeline entirely.

## Policy ownership — the political constraint

<Callout type="warning">
  Applying policies from application code inverts the ownership model
  platform teams bought Omni Gateway for. The SDK is designed around that
  constraint, not against it.
</Callout>

- **The spec file lives in the repo** and is reviewable like any other code
  change.
- **`apply` runs in CI**, under a connected app whose scopes the platform team
  controls — not from a developer's laptop with personal credentials.
- **An allow-list catalog** keeps `fabric.yaml` from referencing arbitrary
  policy assets: it can only reference policies enumerated in
  `policy-catalog.yaml`, a file the platform team owns in a **separate repo**.

The allow-list mechanism ships even before anyone asks for it. Its absence is
what gets an SDK like this banned in a security review — its presence is what
gets a platform team to say yes.

See [Governance lint](/provisioning/governance-lint) for the check that runs
before any of this reaches `apply`, and [Spec format](/provisioning/spec) for
the `fabric.yaml` shape being diffed here.
