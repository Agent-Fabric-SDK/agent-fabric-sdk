You keep writing LangGraph, Google ADK, Strands, LlamaIndex, CrewAI, the OpenAI
Agents SDK, the Anthropic SDK, or Microsoft Agent Framework code exactly as you
do today. The SDK wires those frameworks to your organisation's governed **Omni
Gateway LLM proxy** so every model call is authenticated, attributed, and
policy-checked — and it hands you back your framework's **own native objects**,
never a wrapper you have to code around.

<Callout type="info">
  **"Agent Fabric" is a MuleSoft (Salesforce) product name**, not a generic
  term. This project is an SDK *for* that product; it is descriptive, not a
  first-party release. See [§0.4 in the README](https://github.com/Agent-Fabric-SDK/agent-fabric-sdk).
</Callout>

## The one design rule

> **Adapters return the framework's native object — never a wrapper.**

`fabric.langgraph.chat_model("gpt-4o")` returns a real `langchain_openai.ChatOpenAI`.
`fabric.llamaindex.llm("gpt-4o")` returns a real `OpenAILike`. You can hand these
straight to `create_agent`, a LlamaIndex query engine, a Strands `Agent`,
and so on. If you ever want to drop the SDK, you eject to three lines of native
constructor code — every framework page shows you exactly which three.

## Make a governed call

The Python SDK returns native framework objects. From any other language you hit
the *same* governed proxy over its OpenAI-compatible HTTP API — the verified base
URL plus the `client_id` / `client_secret` headers. (No first-party TypeScript
SDK yet.)

<Tabs items={['Python (async)', 'Python (sync)', 'TypeScript', 'cURL']}>
<Tabs.Tab>

```python
from agent_fabric.integrations.langgraph import chat_model

# A real langchain_openai.ChatOpenAI, already pointed at your governed proxy.
model = chat_model("gpt-4o", temperature=0)
reply = await model.ainvoke([("user", "Explain quantum computing in simple terms.")])
print(reply.content)
```

</Tabs.Tab>
<Tabs.Tab>

```python
from agent_fabric import Fabric

# A real openai.OpenAI, already pointed at your governed proxy — no event loop.
with Fabric.from_env() as fabric:
    client = fabric.llm.client(sync=True)
    reply = client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": "Explain quantum computing in simple terms."}],
    )
    print(reply.choices[0].message.content)
```

</Tabs.Tab>
<Tabs.Tab>

```typescript
const base = process.env.AGENT_FABRIC_LLM_PROXY_URL!;   // ends in "/", no /v1
const resp = await fetch(`${base}chat/completions`, {
  method: "POST",
  headers: {
    "content-type": "application/json",
    client_id: process.env.AGENT_FABRIC_LLM_PROXY_CLIENT_ID!,
    client_secret: process.env.AGENT_FABRIC_LLM_PROXY_CLIENT_SECRET!,
  },
  body: JSON.stringify({
    model: "gpt-4o",
    messages: [{ role: "user", content: "Explain quantum computing in simple terms." }],
  }),
});
console.log((await resp.json()).choices[0].message.content);
```

</Tabs.Tab>
<Tabs.Tab>

```bash
curl "${AGENT_FABRIC_LLM_PROXY_URL}chat/completions" \

  -H "client_id: ${AGENT_FABRIC_LLM_PROXY_CLIENT_ID}" \
```

## What is live today

<Callout type="default">
  **Pillar 1 (governed model access) is live-verified** against a real Anypoint
  sandbox: the proxy base-URL shape (`https://<ingress>/<instance>/`, no `/v1`),
  the `client_id` + `client_secret` consumer-auth header pair, the attribution
  headers, and the four policy rejection shapes (auth `401`, PII `403`,
  token-budget `429`, upstream passthrough). The framework-free client and all
  eight adapters are wired to that verified contract.
</Callout>

What is **not** yet unblocked — and why the SDK raises a clear error instead of
guessing — is covered honestly on the [Verification policy](/concepts/verification)
page. In short: Pillar 2, Pillar 3, and the exact framework *constructor
signatures* still need live confirmation, and code paths that depend on an
unverified endpoint, header, or class name raise
`NotImplementedError("blocked on verification: …")` rather than fabricate one.
