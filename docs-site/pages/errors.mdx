# Governed error taxonomy

The proxy doesn't just pass model calls through — it enforces policy. When it
rejects a call, the SDK turns the response into a **typed exception** so you
branch on the governance outcome instead of parsing bodies.

## The four live-verified rejection shapes

These four shapes are live-verified against the sandbox proxy. The critical
lesson: **neither the status code nor the shape of the `error` value alone is a
sufficient discriminator** — a `403` can be PII (a policy block) *or* auth, and
the same nested-object envelope is emitted by both the upstream provider and a
gateway policy. The authoritative discriminator is the error **`type`** plus
specific headers.

| Rejection | HTTP | Discriminator | Maps to |
|---|---|---|---|
| Client-ID enforcement (auth) | `401` | flat `{"error":"…"}` + `www-authenticate: Client-ID-Enforcement` | `AuthError` |
| PII detected | `403` | nested `{"error":{type:"pii_detected"}}`, **no** `www-authenticate` | `PIIDetected` (parses `entities`) |
| Token rate limit | `429` | **empty body**; `x-token-reset` header (ms) | `TokenBudgetExceeded` (`retry_after` derived) |
| Upstream provider error | 4xx | nested `error` object **with** `x-llm-proxy-*` routing headers | `UpstreamModelError` / passthrough |

`PIIDetected` is checked **before** the generic 401/403→auth rule, precisely
because a PII block is a `403` that is *not* an auth failure.

## The exception tree

All importable from `agent_fabric`:

```
FabricError                     # base of the whole tree
├─ ConfigError                  # misconfiguration (raised locally, pre-flight)
├─ AuthError                    # 401 — bad/missing consumer credentials
├─ PolicyViolation              # base for every governance rejection
│  ├─ PIIDetected               # 403, type=pii_detected; .entities
│  ├─ TokenBudgetExceeded       # 429; .retry_after (seconds)
│  ├─ PromptInjectionBlocked    # (shape not yet captured — falls through today)
│  └─ ContentSafetyBlocked      # (shape not yet captured — falls through today)
└─ UpstreamModelError           # provider error passed through the proxy
```

## Bridging from the raw client

<Callout type="warning">
  `fabric.llm.client()` is the **OpenAI SDK**, so on an HTTP failure it raises
  `openai.APIStatusError`, **not** a `FabricError`. Bridge into the taxonomy by
  applying `classify()` to the error's `.response`.
</Callout>

```python
import openai
from agent_fabric import PIIDetected, TokenBudgetExceeded, AuthError
from agent_fabric.core.errors import classify

try:
    resp = await client.chat.completions.create(model="gpt-4o", messages=msgs)
except openai.APIStatusError as e:
    governed = classify(e.response)          # -> a FabricError subclass
    if isinstance(governed, PIIDetected):
        print("blocked, entities:", governed.entities)
    elif isinstance(governed, TokenBudgetExceeded):
        print("slow down; retry after", governed.retry_after, "s")
    elif isinstance(governed, AuthError):
        print("bad credentials:", governed)
    else:
        print(f"{type(governed).__name__}: {governed}")
except openai.APIConnectionError as e:
    print("could not reach the proxy:", e)
```

## Not-yet-captured shapes

Prompt-injection and content-safety rejection **bodies** are not yet captured, so
today they fall through to a generic `PolicyViolation` rather than their specific
type. This is deliberate (§0.3) — we don't invent a discriminator we haven't
observed. See [Verification policy](/concepts/verification).
